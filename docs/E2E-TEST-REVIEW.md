# E2E test review — 9 September 2026

Historical review of commit `141f6c8ec67b87a97f639620d832d417537853da`: **142 distinct cases across 52 files**, registered for **284 project executions** in Playwright (before runtime project skips and retries). The separate Solothurn config runs a subset of these same cases. The subsequent migration is documented in [E2E-TEST-MIGRATION.md](E2E-TEST-MIGRATION.md). The recommendations below describe the original suite; source links are pinned to the reviewed revision.

Most scenarios protect useful behavior, but many do not need a full animated WebGL application. Move data matrices and React state/effect coverage to Vitest, while retaining a smaller set of real browser integration tests. A file named “terrain” is not by itself a reason to keep every case in Playwright.

Decision meanings:

- **Keep**: the case has a clear browser dependency. It may still be shortened or combined with an adjacent scenario.
- **Split**: retain its browser-specific assertions; move the exhaustive data, state or copy assertions to Vitest.
- **Vitest**: migrate the behavior to pure or mounted component/hook tests, then remove this standalone E2E case. Do not delete it merely because some helper logic already has tests.
- **Consolidate**: the browser interaction is repeated elsewhere. Preserve any unique data/state assertions in Vitest and merge the browser portion into a representative flow.

A practical initial target is about **35–45 concise browser scenarios**, with Chromium renderer checks and a focused WebKit touch/layout/lifecycle subset. This is a design target, not a measured runtime promise. Keep brief route-specific mount tests until component integration covers their separate wiring; shared renderer code alone does not prove that every route is wired correctly.

## Highest-value browser coverage

Keep real coordinate-based station/train/aircraft/road selection; hover/focus/touch distinctions; native dialog focus; desktop/mobile geometry and overflow; actual worker startup/transfer/termination; mounted geometry buffer changes; lazy module failures; a few share-and-reload paths; and representative map/terrain/orbit transitions. Fake timers and a stub canvas cannot establish these properties.

Terrain coverage should distinguish the scenic Rigi renderer, timetable-driven Rigi, the common measured-terrain renderer, and combined Glion’s two different terrain legs. Retain real playing transitions at a tunnel/gallery boundary: losing clock ownership when one scene unmounts is a real integration risk. Exhaustive station/direction/mask matrices belong below that layer.

## Existing fast coverage and missing layer

There is already strong Vitest coverage in `src/studies` and `scripts`, including:

- `explore.test.ts` and `additional-regions.test.ts`: URL round trips, defaults, private-parameter exclusion, regional dates and copy.
- `cantonal-road-pilot.test.ts` and individual recording tests: gap boundaries, final observations, mismatched identity, recording selection and topology.
- `rigi-sequence.test.mjs`, `rigi-timetable-terrain.test.mjs`, `jungfrau-ascent.test.ts`, `gornergrat*.test.ts`, `glion-playback.test.ts`, `glion-terrain.test.ts` and the other mountain suites: actual calls, phase boundaries, dwell interpolation, reverse geometry and invalid bindings.
- `network-ui-index.test.ts`: real schedule counts, selection subsets and search ordering.
- `map-selection.test.ts`, `trail-worker-client.test.ts`, `label-frame-budget.test.ts`, `gleislicht-hub-batching.test.ts`: geometry/picking, worker scheduling/fallback, budgets and installed renderer transformation.

For example, the Rigi E2E exact dwell value `0.6566329989400922` and the same 48780/48840/48960 times already have direct assertions in `scripts/rigi-timetable-terrain.test.mjs`. Gornergrat Vitests cover all 26 ascents and all 26 descents, rather than just one browser itinerary.

The missing layer is **mounted React component/hook integration**. The current Vitest configuration uses the default Node environment, with no declared DOM test environment or Testing Library dependencies. Existing UI tests use server-rendered markup; that does not execute client effects or user interactions. Add a scoped DOM environment and component harness, keep real production state/validators, stub only expensive scenes and external I/O, and exercise effects with controlled promises/timers. Some application orchestration still lives in `App.tsx`; extract a focused hook/controller where that makes testing substantially simpler. Test the production implementation, not a new test-only state machine.

Prioritize `CantonalPilotControls` and app selection wiring, regional morning/day loading and restoration, `useUiText` races, journey controls and clock ownership. Test deferred response completion after cancellation and unmount explicitly. Keep one full browser success/retry flow per distinct integration family while migrating.

## Assertions to repair or narrow

1. **Saved screenshots are not visual regression assertions.** The suite calls `page.screenshot(...)` but has no screenshot comparison assertions. Keep captures for optional review/debugging, or introduce a small deterministic visual suite. Remove fixed camera-settling sleeps that only serve unasserted screenshots from routine functional tests.
2. **The core `beforeEach` always starts the WebGL app.** Even methodology and telemetry tests pay for a national map before navigating elsewhere. Move direct-entry tests outside that hook. Some runtime-skipped cases also have a test-body skip after hook setup.
3. **Core Air/AUTO lazy checks attach listeners too late.** In `gleislicht.spec.ts`, request listeners are added after `beforeEach` has navigated and waited for the canvas. The zero-request assertions can miss eager loads during startup; the 150 ms sleeps do not fix this. Listen before navigation.
4. **“AUTO progressively adopts…” does not establish adoption.** It only checks ASTRA wording also asserted in the ordinary morning-road test. Assert the loaded minute and a changed snapshot/count derived from its fixture.
5. **“Airport hero follows the study clock…” never seeks the clock.** It switches to arrivals and checks that a row exists; add a fixed-time board assertion and verify selecting a row selects the expected flight, not just that the board disappears.
6. **“Methodology … without the visual client” runs with JavaScript and first loads the client.** A direct JS-disabled browser check would test the stated promise. Static provenance can be checked without WebGL.
7. **“Telemetry is opt-in and remains on-device” only checks UI copy at `?perf=1`.** Add default-off coverage and verify production telemetry transport behavior; its own label is not evidence of privacy.
8. **Midnight tests only assert positive counts.** They do not identify a train from the preceding service day. Use a fixture with a known prior-day trip, exact midnight boundary and matching source identity in Vitest.
9. **Several overflow checks happen only after switching through all languages.** Check each retained long-text layout explicitly; a final Italian check says nothing about earlier German/French layout.
10. **Some scene tests inspect private R3F roots and Vite source URLs.** They are valuable dev-server renderer integration tests, not production-bundle smoke tests. Preserve a small built-artifact navigation/worker/lazy-import smoke alongside them if deployment assurance is intended. This is an additional gap, not a reason to keep all duplicated cases.
11. **Negative race assertions need a settled stale response.** Releasing a response gate then checking already-correct state can pass before that response is processed. Vitest deferred promises make the order explicit; browser variants should also wait for completion before proving state stays unchanged.

`data-rendered=true` in the shared measured scene is set after three R3F frames. That is useful lifecycle evidence, but does not prove the terrain pixels, vehicle orientation or visual quality are correct.

## Migration order

1. Add the component harness, then migrate recording variants, malformed inputs, retry variants, stale-response races, frequency labels and count/selection state. Preserve existing domain assertions rather than duplicating them.
2. Parameterize regional date/path/search/share coverage in Vitest. Keep one full regional browser flow, one retry, and a small layout matrix. Cover distinct flat versus date-prefixed asset layouts before removing their smokes.
3. Move complete mountain itineraries to component tests using existing real binding/phase functions. Retain concise renderer mount, map return and clock-handoff tests, including Glion’s two terrain legs and Territet’s passing-loop/context-track case.
4. Consolidate repeated core search/filter/dialog setups, remove screenshots-only sleeps, and restrict browser projects according to actual engine/input risk. Do not try to solve software-WebGL contention simply by increasing workers.
5. Measure the new suite in CI. Current workflow already documents an earlier ~15-minute Chromium run versus ~6-minute WebKit run and shards Chromium across two runners; those are historical comments, not timings measured in this review.
